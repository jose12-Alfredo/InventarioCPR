# Configuración local de Neon y Cloudinary

La autenticación y el acceso móvil privado se documentan en `SECURITY.md`. La migración Identity se aplicó **solo a `test-migracion-inicial`**; los perfiles habituales de Rider y `https-identity-local` abren HTTPS con Identity. El modo anónimo existe únicamente bajo el perfil explícito `anonymous-tests-local` en loopback. Existe **una cuenta administradora ficticia y tres roles de prueba**; el bootstrap temporal fue retirado del código. Render está preparado en código y Docker, pero no configurado ni desplegado; el acceso LAN sigue sin habilitarse. Consulta `DEPLOYMENT.md` antes de preparar Production.

## Credenciales sin consola ni repositorio

En Rider, sobre `InventarioCPR.csproj`, abre **Manage User Secrets** (o la opción equivalente de Visual Studio) y edita el archivo local `secrets.json` que abre el IDE. No pegues credenciales en el chat, comandos, `appsettings*.json` ni archivos del repositorio. El proyecto ya tiene `UserSecretsId`; ASP.NET Core carga User Secrets en entorno `Development`. No ejecutes `dotnet user-secrets list` ni actives registros de configuración, EF SQL sensible o trazas de solicitudes HTTP con tokens.

Estructura del archivo local (sustituir los marcadores *solo en el editor local*):

```json
{
  "ConnectionStrings": {
    "NeonDirect": "Host=<host-de-neon>.neon.tech;Port=5432;Database=<base-existente>;Username=<usuario>;Password=<contraseña>;SSL Mode=VerifyFull"
  },
  "Cloudinary": {
    "CloudName": "<nombre>",
    "ApiKey": "<clave>",
    "ApiSecret": "<secreto>"
  }
}
```

Usa el host de la cadena de conexión de Neon, con o sin `-pooler`. Si Neon entrega una URL `postgresql://usuario:contraseña@host:puerto/base?sslmode=verify-full&channel_binding=require`, conviértela **solo en el editor local de User Secrets** a `Host=<host>;Port=<puerto>;Database=<base>;Username=<usuario>;Password=<contraseña>;SSL Mode=VerifyFull;Channel Binding=Require`. Decodifica los componentes escapados con `%` de la URL antes de pasarlos al formato Npgsql, especialmente usuario y contraseña; no copies la URL literal a `NeonDirect`. La aplicación obliga `SslMode=VerifyFull` y verifica el certificado TLS; no desactives la verificación. No se ejecuta `EnsureCreated`, `Migrate` ni una migración al iniciar. El diagnóstico solo realiza consultas de lectura.

Para verificar sin imprimir credenciales, configura `ASPNETCORE_ENVIRONMENT=Development` en el perfil de ejecución de Rider y ejecuta `dotnet run -- --check-connections` desde la carpeta del proyecto, deteniendo antes cualquier instancia que bloquee la salida de Rider. En PowerShell local, también puedes ejecutar `$env:ASPNETCORE_ENVIRONMENT='Development'; dotnet run -- --check-connections`. El diagnóstico realiza `SELECT 1`, exige TLS con certificado verificado por Npgsql (`SSL Mode=VerifyFull`), muestra el nombre de base y enumera solo esquemas/tablas de usuario mediante `pg_catalog.pg_tables`. No se usa `pg_stat_ssl` para comprobar TLS del cliente: con el pooler de Neon esa vista refleja la conexión interna del pooler a PostgreSQL. Cloudinary efectúa una consulta autenticada de **solo lectura** de uso de cuenta mediante el SDK. No imprime secretos, detalles de errores ni respuestas completas de las API. Un fallo se comunica indicando la etapa y el tipo de excepción, sin incluir la cadena de conexión.

El mecanismo de entrega `authenticated` protege originales y derivados según [la documentación de Cloudinary](https://cloudinary.com/documentation/control_access_to_media#authenticated_media_assets). La consulta de uso verifica la API, **no** prueba la entrega de un recurso `authenticated` en esta cuenta: sin subir una imagen o disponer de una evidencia de prueba existente no puede confirmarse empíricamente ese punto. No se proporcionan enlaces firmados al navegador.

## Rama aislada para probar la primera migración

En la consola de Neon, abre el proyecto de InventarioCPR y selecciona la rama **`test-migracion-inicial`** (créala desde la rama deseada si aún no existe, sin copiar datos empresariales). En **Connect**, selecciona esa rama, `neondb` y el rol correspondiente. Anota **solo el hostname del endpoint** (`ep-...neon.tech`, con `-pooler` si se va a usar el pooler), junto con el ID de la rama `br-...`; el nombre de base `neondb` no identifica la rama. Consulta también el host de la conexión de desarrollo y comprueba que es distinto. No pegues aquí la URL ni la contraseña.

En el IDE, abre **Manage User Secrets** de `InventarioCPR.csproj` y añade dentro de `ConnectionStrings` una clave adicional `NeonMigrationTest` con la cadena Npgsql de **esa rama**, siguiendo el formato mostrado arriba. Añade además `"NeonMigrationTest": { "ExpectedHost": "<host-del-endpoint-de-esa-rama>" }` al nivel raíz del mismo `secrets.json`. Conserva `NeonDirect` sin modificar. Comprueba en el editor que el valor `Host` de `NeonMigrationTest` coincide con el endpoint de la rama `test-migracion-inicial` mostrado en Neon; un host `-pooler` corresponde al mismo endpoint sin el sufijo `-pooler`. Si prefieres, comunica únicamente el hostname y el ID `br-...` (no son credenciales) para verificar la correspondencia con la consola. `ASPNETCORE_ENVIRONMENT=Development` solo permite cargar User Secrets y no identifica una rama de Neon. El modo `--check-migration-test-config` informa únicamente si la clave existe; no conecta ni revela el secreto. Las pruebas PostgreSQL en `InventarioCPR.Tests` exigen ambas claves, comparan host y base y rechazan el endpoint de `NeonDirect`. **La comprobación decisiva de la rama sigue siendo la asociación del hostname/ID con el nombre en la consola de Neon**.

El modo `--check-migration-test-connection` comprueba con lecturas que `NeonMigrationTest` apunta a un host diferente de `NeonDirect`, coincide con `ExpectedHost`, abre con TLS `VerifyFull`, consulta `neondb` y cuenta tablas e historial EF. Se confirmó el nombre de rama comparando su hostname con la pantalla Connect de Neon. Para EF CLI se añadió un factory de diseño que exige `-- --migration-test` y el endpoint aprobado: no hay fallback a `NeonDirect`. La migración inicial se probó **solo en `test-migracion-inicial`**. No ejecutes `database update` en otra rama sin nueva autorización.

Para registrar **solo datos ficticios**, `ConnectionStrings:NeonDevelopmentApp` (nombre de clave mantenido por compatibilidad local) está configurada en User Secrets con el host `-pooler` de la misma rama **`test-migracion-inicial`**, `SSL Mode=VerifyFull` y `Channel Binding=Require`. La aplicación comprueba que ese endpoint coincide con la conexión aislada de migración y difiere de `NeonDirect`, y usa pooling. `--check-development-app` consulta tablas e historial sin imprimir credenciales. Tras confirmar en Neon el nombre y host de la rama de pruebas, se configuró `"NeonDevelopmentApp": { "BranchConfirmed": "test-migracion-inicial" }` en User Secrets; sin ese marcador el servidor rechaza escrituras y deshabilita el botón de guardar. El nombre del entorno .NET `Development` **no identifica la rama de Neon**. La app funcional arranca solo en `Development` y atiende únicamente `127.0.0.1` hasta implementar identidad y autorización empresarial. La captura del diálogo de expiración mostró «Expire branch on» desmarcado, con la fecha deshabilitada; si modificaste esta opción, pulsa «Confirm» para guardar el estado deseado.

## Alcance y condiciones antes de usar datos reales

- `Infrastructure/Persistence` configura EF Core con la conexión cifrada a Neon. La migración `InitialInventorySchema` se probó en `test-migracion-inicial` y **no se aplicó a `production`**. Revisa los asuntos pendientes de `BUSINESS_RULES.md` antes de autorizar su ejecución en otra rama; no hay importación de Excel ni datos precargados.
- `Infrastructure/Photos` admite JPEG/PNG hasta 10 MB y 25 megapíxeles, comprueba formato decodificado y fotogramas, recodifica sin EXIF y sube con `Type=authenticated`, ID aleatorio y sin sobrescritura. El contrato vive en `Application/Photos`. Los metadatos `CloudinaryPublicId`, `EquipmentId`, `EvidenceType` y `UploadedAtUtc` se modelaron para PostgreSQL; todavía no existe operación que los persista. No se guardan bytes en PostgreSQL.
- Antes de habilitar subida o visualización: implementar identidad empresarial, autorización por equipo y tipo de evidencia en cada solicitud, servicio de aplicación transaccional (incluida gestión de fallo parcial entre Cloudinary y BD), auditoría, y una ruta de descarga en servidor que compruebe permisos antes de obtener el recurso autenticado mediante SDK o URL firmada de vida corta. Nunca devolver URL permanente ni credenciales Cloudinary al navegador. Definir también política antimalware y retención. No se ha expuesto ninguna ruta de fotos.
- El procesamiento de fotografías usa SkiaSharp (licencia MIT) para identificar y recodificar. Se retiró la dependencia directa ImageSharp 3.2.0: sin clave bloqueaba las compilaciones Release; [Six Labors](https://sixlabors.com/pricing/) exige licencia comercial para determinados usos empresariales de dependencia directa, y ofrece licencia Community previa solicitud para quienes reúnan sus condiciones. No se compró ni incorporó ninguna licencia.
