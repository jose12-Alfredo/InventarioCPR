### HTTPS e Identity local para la siguiente prueba

Los perfiles `http`, `https` y `https-identity-local` de `Properties/launchSettings.json` configuran `ASPNETCORE_ENVIRONMENT=Development`, `Security__EnableIdentity=true` y `Inventory__ListenUrl=https://localhost:7228`. El nombre heredado `http` ya no abre HTTP. Incluso sin perfil explícito, Identity es la configuración por defecto. Kestrel usa el certificado de desarrollo de .NET instalado y confiado para `localhost`, sin exportarlo. `dotnet dev-certs https --check --trust` lo confirmó; una petición con validación TLS predeterminada obtuvo HTTPS 200 de `/acceso`. La app escuchó únicamente en `127.0.0.1` y `::1`; las peticiones anónimas a `/inventario`, `/` y `/admin/usuarios` respondieron 302 a `/acceso`, también en POST de administración sin sesión. El login y el logout del administrador de pruebas se comprobaron por HTTPS previamente y no se alteró ese flujo. Para ver el comportamiento nuevo, detener en Rider cualquier instancia anterior que aún escuche en `127.0.0.1:5272` y seleccionar el perfil **`https`** (o `https-identity-local`). Un certificado de desarrollo de `localhost` **no** autoriza acceso desde teléfonos ni otros equipos.

El único modo anónimo es `anonymous-tests-local`, con `launchBrowser=false`: exige simultáneamente `Development`, `Security:EnableIdentity=false`, `Inventory:AllowAnonymousLocalTests=true` y bind exacto a `http://127.0.0.1:5275`. Sin ese opt-in, el arranque anónimo falla. No utilizarlo para datos empresariales. Production/Render no pueden iniciar con Identity deshabilitado. El modo Render se detecta mediante `RENDER=true`, obtiene host y puerto de las variables nativas y exige la conexión Production; escucha HTTP interno y procesa `X-Forwarded-For`/`X-Forwarded-Proto` del proxy antes de redirección y autenticación. La imagen usa `/var/data/keys` para Data Protection; debe montarse un disco persistente. Las instrucciones y bloqueos pendientes están en `DEPLOYMENT.md`.

### HTTPS LAN preparado, no habilitado

Antes de habilitar acceso desde otros equipos, aprobar por separado el procedimiento y configurar en el editor de **Manage User Secrets** (sin pegar secretos en chat, terminal ni repositorio) `Security:EnableIdentity=true`, `Inventory:ListenUrl=https://<IP-privada>:<puerto>`, `Inventory:AllowedOfficeNetwork=<subred-CIDR>`, `Kestrel:Certificates:Default:Path` y `Kestrel:Certificates:Default:Password`. El arranque rechaza una migración Identity pendiente. La URL de escucha se vincula a la IP privada, pero el teléfono puede navegar a un nombre DNS interno que resuelva a esa IP: el certificado debe tener SAN para el **nombre usado por el teléfono**, o SAN para la IP si se navega por IP. Para certificados emitidos por una CA interna, confiar esa CA en Android/iPhone; un certificado público válido para un dominio propio también sirve si el DNS interno resuelve el dominio a la IP privada. El certificado de desarrollo de localhost no basta. Nunca usar `0.0.0.0` ni abrir puertos del router. Las credenciales de Neon y Cloudinary permanecen exclusivamente en el servidor.

- Se añadió exclusivamente el perfil `https-identity-lan` de Rider: `Inventory__ListenUrl=https://192.168.3.70:7443`, `Inventory__AllowedOfficeNetwork=192.168.3.0/24`, `Security__EnableIdentity=true`, sin abrir navegador. No se modificaron los perfiles existentes. **No arrancar ni habilitar todavía**: el servidor exige además `Inventory:LanAccessApproved=true` (sin configurar) y una ruta/contraseña de certificado explícitos en User Secrets; si faltan, el arranque rechaza la conexión LAN. `--check-lan-preparation` confirmó **autorización=False, certificado explícito=False** sin mostrar valores ni abrir puerto. Este perfil no incluye secretos, no abre Firewall y no cambia router ni base de datos.
- El teléfono debe estar en una red Wi-Fi autorizada con ruta hacia `192.168.3.70` y sin aislamiento entre clientes; estar en la misma SSID no garantiza comunicación si hay VLAN, Wi-Fi de invitados, ACL corporativas o aislamiento AP. Confirmar IP del teléfono, DNS interno y alcance de `7443/TCP` con TI antes de solicitar cambios de red. Blazor Interactive Server requiere `wss` en el mismo origen HTTPS para circuitos y reconexión.
- Certificado: solicitar a TI un certificado servidor para un **nombre DNS interno estable** que resuelva a `192.168.3.70` o para la IP si realmente se navegará por IP; debe contener ese nombre/IP como SAN. Si se usa una CA interna, instalar **solo su certificado público** como raíz confiable en cada dispositivo autorizado (Android: Ajustes → Seguridad/credenciales → Instalar certificado CA, ruta variable según fabricante; iPhone: instalar el perfil de CA y habilitar confianza total en Ajustes → General → Información → Ajustes de confianza de certificados). En dispositivos gestionados, seguir MDM/TI. Alternativamente, un certificado público válido para un dominio propio puede usarse con DNS interno que resuelva a la IP privada. **Nunca** distribuir claves privadas de servidor o CA, copiar PFX al celular, desactivar TLS ni reutilizar el certificado de desarrollo de `localhost` para la IP LAN. Guardar PFX fuera del repositorio, contraseña solo en User Secrets.
- URL prevista del teléfono: **`https://192.168.3.70:7443`** solo con SAN IP y CA confiable, o **`https://<nombre-interno-incluido-en-SAN>:7443`** con DNS interno y CA confiable. Sin certificado/dominio acordado, no existe aún una URL LAN que el celular pueda abrir sin error TLS.
- Regla de Windows Firewall **propuesta, no ejecutada** para cuando el usuario y TI autoricen la prueba; en PowerShell elevado y tras conocer la IP real del teléfono: `New-NetFirewallRule -DisplayName 'InventarioCPR-TEST-LAN-7443' -Direction Inbound -Action Allow -Protocol TCP -LocalAddress '192.168.3.70' -LocalPort 7443 -RemoteAddress '<IP-del-celular>' -Profile Public`. Limitar a una IP concreta; si no es estable, acordar reserva DHCP o un alcance mínimo aprobado. No cambiar el perfil de red, otras reglas corporativas ni hacer port forwarding en el router.
- Reversión (solo si la regla llegara a autorizarse): detener la ejecución Rider `https-identity-lan`; `Disable-NetFirewallRule -DisplayName 'InventarioCPR-TEST-LAN-7443'` y luego `Remove-NetFirewallRule -DisplayName 'InventarioCPR-TEST-LAN-7443'` en PowerShell elevado, únicamente para la regla creada. Retirar `Inventory:LanAccessApproved` y rutas/contraseñas del certificado LAN de User Secrets, conservar el PFX/CA según política TI y volver al perfil existente **`https-identity-local`**. No se aplicó ninguno de estos cambios en esta fase.

El bootstrap autorizado se ejecutó correctamente **una sola vez** y su implementación temporal se retiró de `Program.cs` y del repositorio; `--bootstrap-security` ahora rechaza la ejecución. Para retirar el secreto local, abre **Manage User Secrets** de `InventarioCPR.csproj` en Rider y elimina del archivo local las tres claves `Security:Bootstrap:Password`, `Security:Bootstrap:UserName` y `Security:Bootstrap:Email` (o el objeto `Bootstrap` completo), conservando las demás configuraciones. La versión final sin bootstrap conservó login HTTPS y redirigió anónimos a `/acceso`. No se probó aún un circuito Blazor autenticado reconectando desde un dispositivo físico, ni se creó otra cuenta.

### Diagnóstico actual de login y recuperación pendiente

El formulario de `/acceso` aceptaba exclusivamente `UserName`, mientras el usuario ingresaba el correo. Ahora busca primero por usuario y, si se ingresó un correo, mediante `UserManager.FindByEmailAsync`; una prueba PostgreSQL sobre la cuenta ficticia confirmó ambos identificadores sin consultar contraseñas. Chrome/Playwright comprobó que el botón envía POST, incluye antiforgery y muestra un error controlado con usuario inexistente. La instancia de Rider observada en 7228 agotaba el tiempo incluso para GET `/acceso` bajo `JetBrains.Debugger.Worker`, mientras una copia aislada del mismo binario y el proceso reconstruido en el puerto 7228 respondieron normalmente. Si se repite el bloqueo, detener la instancia antigua de Rider y usar **Run** del perfil `https`, no una sesión Debug detenida o atascada.

Cambiar `Security:Bootstrap:Password` no cambia la contraseña ya hasheada en Identity. El diagnóstico mostró que la clave nueva había quedado otra vez bajo `Bootstrap`; el usuario confirmó que era **distinta de las publicadas en el chat**. Una herramienta temporal trasladó el valor **solo dentro de User Secrets**, sin mostrarlo, a `Security:PasswordReset:NewPassword` y retiró el objeto `Bootstrap`. Un procedimiento CLI limitado a Development/HTTPS localhost comprobó una sola cuenta administradora activa y tres roles en `test-migracion-inicial`, y utilizó el token y `ResetPasswordAsync` de `UserManager` para actualizar **solo el hash**. No creó usuarios ni alteró perfiles.

Después, una prueba HTTP HTTPS local, sin exponer la clave, inició sesión **tanto por correo como por usuario**, abrió el inventario y `/admin/usuarios`, verificó cookie Secure/HttpOnly/SameSite y cerró sesión en ambos casos. El secreto `Security:PasswordReset:NewPassword` se eliminó de User Secrets y la comprobación de presencia confirmó que ya no existe tampoco `Security:Bootstrap:Password`. Las herramientas temporales de transferencia, reset y comprobación de sesión se retiraron del código. La cuenta sigue en Neon con **1 usuario activo, 3 roles, 0 intentos fallidos y 0 bloqueos**; el login habitual no requiere el secreto temporal. Las compilaciones estándar Debug y Release terminaron con 0 errores/advertencias, y 4 pruebas filtradas sin escrituras pasaron.

El login conserva ahora el `ReturnUrl` generado por la cookie de Identity: `/` vuelve a Inicio, `/inventario` vuelve al inventario y una ruta profunda local conserva ruta y query. El formulario transporta el destino mediante un campo oculto y también lo mantiene tras un intento fallido. La normalización solo admite rutas locales que comienzan con `/`, rechaza esquemas, destinos `//` o `/\`, controles y valores vacíos; cualquier entrada inválida usa `/`. El resultado exitoso utiliza `LocalRedirect`, que añade la validación local de ASP.NET Core. Logout continúa eliminando la sesión y redirigiendo a `/acceso`.

La primera instancia Rider observada en 7228 se colgaba incluso con GET `/acceso` bajo JetBrains.Debugger.Worker; tras comprobar cero conexiones activas, se detuvo **solo ese proceso**. El mismo binario ejecutado sin ese proceso respondió al formulario y sus POST. Si reaparece una instancia Rider atascada, detenerla con Stop, recompilar y ejecutar el perfil `https` con Run. La última versión compilada respondió HTTPS 200 en `/acceso` y redirigió anónimos (302) de `/inventario` a login. No se probó desde un teléfono físico ni se habilitó LAN.

Tenía cero conexiones establecidas y el CPU no avanzaba. Se detuvo **solo ese `InventarioCPR.exe`**, sin cerrar Rider; una instancia del binario estándar **sin depurador y en el mismo HTTPS 7228** respondió GET 200 y POST de login 302 en Chrome.
